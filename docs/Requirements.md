# MyHomeControl Orchestrator – System Requirements

Version: draft 1 – 2026-10-24

## 1. Purpose and scope

The Orchestrator coordinates two existing services that run on a Raspberry Pi 3:

| Service | Controls | Schedule file |
|---|---|---|
| **Boiler service** | Heater on/off, to keep hot-water capacity at a target | `Cal.json` |
| **Timer service** | General relays switched on/off at fixed times | `TimeCal.json` |

The Orchestrator adds: schedule editing (Google Calendar and a web UI), a status UI, manual override, and an MQTT interface for Home Assistant. It does not replace the heating logic inside the two services.

It is the successor of the existing `BoilerControler.py` (a polling loop that reads the Google Calendars, sends Gmail notifications and commands, and talks to the boiler Pi over its REST API). Behaviour of that script that is kept is listed in section 4.8. The Orchestrator talks to the boiler Pi only through its REST endpoints (section 3.6); there is no FTP/file copy.

## 2. Definitions

- **Capacity**: estimated number of showers available in the boiler. Two values are reported by the status endpoint: `CurrentShowers` is the linear (legacy) calculation, `CurrentShowersnew` is the thermodynamic (new) one. Which one is shown as the primary value is configurable (default: thermodynamic).
- **Target**: capacity the heater should heat up to for a schedule slot.
- **Min**: the minimum level that must be kept in the boiler at all times during the slot's period (from its start until the next slot starts). Whenever the level falls below Min the heater must run, even if Target is not due yet. It is in the same unit as Target (showers, see OQ-15).
- **Slot**: one schedule entry (`DayOfWeek`, `Hour`, plus values). `DayOfWeek` is 1–7 (1 = Sunday, 7 = Saturday). A slot stays in force until the next slot starts.
- **Manual override**: a temporary slot that replaces the schedule for a limited time.

## 3. Existing interfaces (as found in this folder)

### 3.1 `Cal.json` – boiler schedule
Array of `{"DayOfWeek": int, "Hour": "HH:MM:SS", "Target": float, "Min": float}`. The number of slots per day varies (3–5 today).

### 3.2 `TimeCal.json` – timer schedule
Array of `{"DayOfWeek": int, "Hour": "HH:MM:SS", "State": 0|1, "RelayNum": int}`. Currently relay 4 only (on ≈17:30, off 23:00; on-times differ by day by about a minute).

### 3.3 `manual.json` – manual override
Same record format as `Cal.json`, e.g. `[{"DayOfWeek":7,"Hour":"19:00:00","Target":4,"Min":4}]`. Here `DayOfWeek`/`Hour` is the **expiry time** of the override: the boiler service applies the values until that time, then deletes the file and returns to `Cal.json`.

### 3.3a `<n>Timermanual.json` – manual relay override
One file per relay `n` (relays 2–7), in the timer-service format, containing an ON entry at the request time and an OFF entry `duration` seconds later. Example for relay 2: `[{"DayOfWeek":6,"Hour":"13:25:09","State":1,"RelayNum":2},{"DayOfWeek":6,"Hour":"13:27:39","State":0,"RelayNum":2}]` (150 s on Friday). The Orchestrator replaces `BoilerCalander.py`/`TimerCalander.py` as the component that builds schedule files, so it **creates these files itself** (the same way `ReadGmailCalendar.py` builds a `TimerCalander` from ON/OFF tasks, lines 143–144) in the format of FR-PUSH-7, and delivers them to the boiler Pi through the REST interface (FR-LEG-6, OQ-16). The configured name `Timemanual.json` in `Config.py` is superseded by this per-relay pattern.

### 3.4 `temp.txt.current` – not used
The boiler Pi writes this local file, but the Orchestrator has **no access to it**; all boiler data comes through the REST endpoints (section 3.6). The file was moved to `ref files` and is ignored.

### 3.5 Status endpoint – `GET http://<boiler-pi-ip>/status`
The `BoilerStatus` class is the JSON model of this endpoint's response (names without the `_m` prefix). Example:
```json
{ "ActiveYesNo": "Yes", "CurrentShowers": 3.43, "CurrentShowersnew": 4.92,
  "CurrentTemp": [58.06, 54.19, 61.44], "Date": "2026-10-24T16:40:19.707843",
  "HeaterOnOff": "Off", "MinVal": 4.0, "Status": "Manual", "TargetVal": 4.0,
  "TimeToStartMin": 175 }
```
- `CurrentShowers` / `CurrentShowersnew` are already in showers (no scaling needed).
- `Status` is the active mode: `Auto` (following the schedule in `Cal.json`), `Manual` (a `manual.json` override was created, e.g. from the UI, and is in use) or `Off`. Any other value is displayed as-is. The connection-failure placeholder `{"Status": "fail to connect to Manager", "ActiveYesNo": "No"}` is generated by the Orchestrator when the Pi cannot be reached.
- `Date` is ISO 8601 local time without timezone.
- This endpoint is the single source for the status UI and MQTT state. There is no fallback file source. The older `/nicestatus` page of `ManagerRestApi.py` is a legacy basic UI and is not used.

### 3.6 Boiler Pi REST endpoints (from `BoilerControler.py`)
The URLs are built in `Config.py` from `baseRestURL` (currently `http://MARELLYPI3:8000/`, every path ends with `/`). The Orchestrator keeps the same configuration keys.

| Config key | Path | Method | Purpose | Payload |
|---|---|---|---|---|
| `GetStatusURL` | `status/` | GET | Boiler status (section 3.5) | – |
| `GetLogURL` | `log/` | GET | Last ~150 lines of the boiler log | – |
| `GetRelayStatusURL` | `relay/?relay=<n>` | GET | State/audit of relay `n` | – |
| `PostUpdateCalURL` | `updatecalander/` | POST | Replace the boiler schedule (`Cal.json`) | multipart form, file field `file` |
| `PostUpdateRelayURL` | `updaterelaycalander/` | POST | Replace the timer schedule (`TimeCal.json`) | multipart form, file field `file` |
| `PostUpdateManualCalOnURL` | `manualon/` | POST | Legacy: manual boiler ON, the Pi created `manual.json` locally | JSON `{"id": 78912}` as sent by `nice.html` (the e-mail script sends a dummy body) |
| `PostUpdateManualCalOffURL` | `manualoff/` | POST | Legacy: manual boiler OFF, same | same |
| `PostUpdateManualCalURL` (**new**, name proposed) | to be defined | POST | Upload the Orchestrator-built `manual.json` (manual ON/OFF) | multipart form, file field `file` |
| `PostUpdateManualRelayFileURL` (**new**, name proposed) | to be defined | POST | Upload the Orchestrator-built `<n>Timermanual.json`; the Pi takes the relay from the uploaded file name | multipart form, file field `file`, file name `<n>Timermanual.json` |
| – (not in `Config.py`) | `auto/` | POST | Legacy: cancel the override (Auto button of `nice.html`); replaced by an empty `manual.json` upload | same |
| – (not in `Config.py`) | `history/` | GET | Last 24 h of samples for the chart | – (format in section 3.8) |
| `PostUpdateManualRelayOnURL` | `relayon/` | POST | Switch a relay on for a duration | JSON `{"swith": <relay>, "duration": <seconds>}` (key spelled `swith`) |
| `PostUpdateManualRelayOffURL` | `relayoff/` | POST | Switch a relay off (defined in `Config.py`, payload not seen in the code; assumed same as relay on) | JSON, see OQ-14 |

Response bodies are returned as text. Failures (timeouts, connection errors) are caught and reported as an error, never raised into the main loop.

### 3.7 Existing Python modules
`BoilerCalander.py` / `TimerCalander.py` (schedule models with load/save/diff/JSON; `TimerCalander.py` is the same code the timer service uses to read the timer file, so its parsing rules are a compatibility constraint, see FR-PUSH-7), `BoilerControler.py` (main loop), `ReadGmailCalendar.py` (calendar reader), `GmailMessages.py` (send/read/delete mail), `Config.py` (settings). `Astro.py` (sun/moon times) is also present. Still missing from the folder: `Name2RelayNum.py` (relay names) and `remoteSSH.py` (OQ-4).

How `Astro.py` works: it turns the address from `Config` (street, city, country) into coordinates with the online Nominatim geocoder (`geopy`), then computes times with the `astral` library. Defects: the geocoding call needs internet every time a calendar is read (and has no timeout or cache, so it can hang the loop); the conversion to local time adds the Pi's *current* UTC offset, so times for a date on the other side of a daylight-saving change are one hour off; `twilight` and `midnight` are not values returned by `astral`'s `sun()` and raise an error; the `moonrise`/`moonset` calls can fail on days without a moonrise. `Config.py` also holds the SSH user name and password in clear text; this is a security risk (the password has been seen in this session, so change it once the secrets file exists).

How `ReadGmailCalendar.py` works (this defines the calendar format, section 4.1):
- It reads the **primary** calendar of the Google account, one week (Sunday 00:00 to Saturday 23:59) around today, with recurring events expanded, up to 100 events. Day of week is taken from each event's date (Sunday = 1).
- An event's **title** (`summary`) is the command. Case-insensitive, separators `; , : =` or spaces:
  - `Boiler: target=3.5; min=2` → a boiler slot starting at the event's start time with that Target and Min.
  - `Timer: relaynum 4 5 start sunset +30 end 23:00` / `Timer: relaynum <numbers or names> duration 3600` → an ON entry at the event's start time (or at a sun/moon time `sunrise|sunset|dawn|dusk|noon|midnight|moonrise|moonset|twilight` with an offset in minutes) and an OFF entry at the end time, the end astro time, or start + `duration` seconds. If the end is before the start, the OFF is on the next day. Relay names are translated by `Name2RelayNum`.
- Because astro times change daily, `TimeCal.json` contains slightly different times per day (as seen in the sample), so the file is regenerated weekly or when the sun times shift.
- Defects: the time zone is hard-coded as `+02:00` (wrong in Israel summer time, which is +03:00); `Astro.addres(...)` location comes from `Config`; typos (`inbex`, `offet`) mean the "hours → minutes" offset conversion never applies and a title starting with the bare word `boiler`/`timer` would crash; a Boiler title with `target` but no `min` after it raises an index error; the file parses command-line arguments at import time; the scope is calendar read-only; credentials are saved under the current directory in `.credentials`.

Other known defects to avoid when reusing the code:
- Schedule files are parsed by splitting strings, not with `json`; `Target`/`Min` are kept as strings after loading.
- `Post()` re-posts with an undefined body after a file upload (the file POST succeeds but the function then fails and returns "fail to post data").
- `ProcessCalendar` overwrites its `skip` flag so the "fail to read calendar" case is not skipped; the `reset` e-mail command uses attributes (`.date`, `.capacity`) that the status dict does not have; `status` and `on`/`off` e-mail commands test `Status == "on"`, which does not match `Auto/Manual/Off`.
- `oauth2client` is deprecated; the new code should use `google-auth` / `google-auth-oauthlib`.

### 3.8 Existing web page `nice.html` (served by the boiler Pi at `/nicestatus`)
This is the **functional reference only**: the new UI is a new design, not a copy of this page (FR-UI-1). What it does:
- Polls `/status` every 10 s and shows gauges: showers (0–6, from `CurrentShowers`), showers new (0–10, `CurrentShowersnew`), and three temperature gauges (0–70 °C, yellow → orange → red). It maps `CurrentTemp[2]` to "Upper", `CurrentTemp[0]` to "Mid" and `CurrentTemp[1]` to "Lower". These are fixed sensor positions; the new UI keeps them (FR-UI-1b).
- Shows "Mode is `<Status>`" and "Heater is: `<HeaterOnOff>`" with an icon.
- One toggle button: when `HeaterOnOff == "Off"` it shows **On** (POST `/manualon`), otherwise **Off** (POST `/manualoff`). A separate **Auto** button POSTs `/auto`. All three send body `{"id": 78912}` (a fixed id, kept in configuration). The page does not re-read the status after the click; it shows the change at the next 10 s poll.
- Draws a 24 h line chart every 10 min from `GET /history`: a text list of rows `[year,month,day,hour,min,sec,showersOld,min,target,heaterStatus,showersNew],...` (columns: Avail Showers old, Min Showers, Target Showers, Heater Status, Avail Showers). The month is written 1-based by the boiler Pi (October = 10, seen in a real answer on 2026-10-26); the page feeds it straight into a JavaScript `Date` (0-based), so its chart dates are a month ahead, which went unnoticed. The new UI must not copy that. The answer is also not valid JSON: no outer brackets and zero-padded time fields (`06`).
- Weaknesses to fix: synchronous XHR (blocks the page), Google Charts and JustGage loaded from the internet, no error handling when `/status` is unreachable, fixed 900×500 chart (not mobile friendly), toggle based on heater state rather than on `Status`.

### 3.9 Relay names (`Name2RelayNum.py`)
| Relay | Name | Relay | Name |
|---|---|---|---|
| 0 | BoilerHeat | 4 | GardenLights |
| 1 | BolerLight (sic) | 5 | intercom |
| 2 | GardenRoof | 6 | spareGround2 |
| 3 | SpareRoof | 7 | spareGround2 (duplicate name) |

- Names are matched case-insensitively in calendar titles (`Timer: relaynum gardenlights start sunset`), so a name must be one word without spaces or the separators `; , : = + -`.
- Relays 0 (boiler heater) and 1 are controlled by the boiler service and are not available to manual relay commands: the e-mail `switch` command accepts relays 2–7 only, and the UI and MQTT offer the same set. `TimeCal.json` currently uses relay 4 (GardenLights).
- The UI, MQTT entity names and e-mails show the relay name with its number. The name list is read from the same configuration as the calendar parser (one source of truth), and the duplicate `spareGround2` for relays 6 and 7 is reported at startup because a name must map to one relay (typo to fix, e.g. `spareGround3`).

## 4. Functional requirements

### 4.1 Schedule configuration (FR-CFG)

- **FR-CFG-1** The system shall read the boiler schedule and timer schedule from Google Calendar.
- **FR-CFG-2** The system shall allow editing both schedules in a web UI.
- **FR-CFG-3** Calendar and UI shall be usable independently or together, selectable by configuration (`calendar`, `ui`, `both`).
- **FR-CFG-4** A change made in the UI shall be written to Google Calendar. A change made in Google Calendar shall appear in the UI.
- **FR-CFG-5** Any accepted change shall regenerate `Cal.json` / `TimeCal.json` and push them to the boiler Pi (section 4.6).
- **FR-CFG-6** Calendar event format: the existing format of `ReadGmailCalendar.py` is kept unchanged (section 3.7): one calendar (primary, configurable id), the event title is `Boiler: target=<x>; min=<y>` or `Timer: relaynum <n|name ...> [start <time|astro±min>] [end <time|astro±min>] [duration <sec>]`, the event start time and weekday give the slot, and recurring weekly events are expanded for the current week. Events whose title does not parse are ignored (and listed in the log).
- **FR-CFG-6a** Astro times (sunrise, sunset, dawn, dusk, noon, midnight, moonrise, moonset, twilight) are resolved to clock times with the `astral` library for the configured location, so `TimeCal.json` always contains clock times. The time zone and its daylight-saving offset come from the configured zone name (e.g. `Asia/Jerusalem`) applied to the date of the event, not from a fixed `+02:00` or the current offset. The location is geocoded once from `Street`/`City`/`Country`, cached on disk, and can be overridden with latitude/longitude in the configuration, so the Orchestrator needs no internet for this at runtime. `twilight` means civil dusk and `midnight` means solar midnight (computed with `astral.sun.midnight`); an astro event that cannot be computed is skipped and logged, never fatal.
- **FR-CFG-6b** For UI → calendar write-back (FR-CFG-4) the UI edits slots in the same event-title syntax; creating or changing an event needs the read-write calendar scope. Astro-based timer events are shown in the UI with their expression (e.g. "sunset +30") and are only editable as an expression, so write-back never replaces them with a fixed time.
- **FR-CFG-7** Sync shall be two-way with conflict handling: the most recent modification wins, based on timestamps. Both sides shall be logged when a conflict is resolved.
- **FR-CFG-8** Invalid input (bad time, a value outside 0..5, unknown relay, two different slots at the same time) shall be rejected with a clear message and shall never overwrite the last valid file.
- **FR-CFG-9** Calendar polling interval shall be configurable (default 5 min). Calendar changes shall be applied within one interval.
- **FR-CFG-10** Writes shall be atomic (write temp file, then rename) and the previous version kept as a backup.

### 4.2 Status UI (FR-UI)

- **FR-UI-1** The UI is a **new design** (not the current `nice.html` look). It must show everything `nice.html` shows (section 3.8) and more: heater on/off, mode, active yes/no, three temperature levels, both shower values, target, min, minutes to start (`TimeToStartMin`) and the 24 h history chart from `history/`. The mode shown is always the `Status` value of the status endpoint (`Auto`, `Manual` or `Off`).
- **FR-UI-1b** Temperature levels are fixed sensor positions, as in the legacy page: `CurrentTemp[2]` is Upper, `CurrentTemp[0]` is Mid and `CurrentTemp[1]` is Lower; the values are never sorted (on a hot day the water entering at the bottom can be warmer than the water above it for some time). They are shown as a vertical boiler graphic. The same assignment is used for MQTT. Each level is coloured by what the water means for a shower: below 30 °C cold (blue), 30-40 lukewarm (teal), 40-50 hot and good for a shower (green), 50-60 very hot (amber), 60-70 scalding (red), 70 and above extremely hot (dark red); the number stays in the block, so colour is never the only signal.
- **FR-UI-1a** The page calls the Orchestrator's own API, which relays to the boiler Pi (no cross-origin calls from the browser). Charts and gauges use libraries stored on the Orchestrator, not CDNs.
- **FR-UI-2** The page refreshes automatically (default every 10 s) and shows the age of the data. It shows a clear "stale" warning if the reading is older than a configurable limit (default 5 min).
- **FR-UI-3** The page shows the next scheduled slots, any active manual override with its expiry time, and relay states.
- **FR-UI-4** The page has schedule editors for the boiler and the timer (FR-CFG-2).
- **FR-UI-5** The page has **On**, **Off** and **Auto** buttons (section 4.3). The buttons show the current mode (the active one is highlighted), are disabled while a request is in flight, and show success or error after the status is re-read.
- **FR-UI-6** The UI needs no internet access except for Google sync, and is fully usable on any screen from 320 px wide (phone, portrait or landscape) up to a desktop, sizing itself automatically with no horizontal page scroll:
  - responsive layout: three columns on desktop, one column on a phone; the header chips wrap and the tabs scroll sideways;
  - schedule and timer tables turn into stacked cards on narrow screens, dialogs become bottom sheets;
  - touch targets at least 40–44 px; input text 16 px so phones do not zoom on focus; safe-area insets honoured (notch);
  - the 24 h chart is drawn at the real screen width (fewer axis labels on a phone) and redrawn on rotation or resize;
  - light and dark theme follow the device setting.
  The mock `ui-mock/index.html` is the reference and is checked at 320, 375, 414, 768 and 1280 px.
- **FR-UI-7** Access control: the UI is reachable on the LAN only. Optional username/password (configurable) for edit and manual actions.

### 4.3 Manual on/off (FR-MAN)

- **FR-MAN-1** Manual control uses the boiler Pi's own endpoints (OQ-16, resolved 2026-10-28; see `ref files/ManagerRestApi.py`). The Orchestrator sends **one POST without a file** and the boiler Pi builds `manual.json` itself, with its own clock: On = `POST manualon/` (the boiler Pi sets Target and Min 4 for about 3 hours), Off = `POST manualoff/` (Target and Min 0 for about an hour), Auto = `POST auto/` (the boiler Pi deletes `manual.json`). The Orchestrator does not build manual files, choose a level or compute an expiry time. Each command is sent once and never retried (CS-10).
- **FR-MAN-2** Because the boiler Pi chooses the level (4 showers), the heater limit of 5 holds by construction and no fresh status is needed to send a command. A request the boiler Pi cannot honour, such as a chosen duration (`hours` in an MQTT command), is **refused, not ignored**. The levels "current showers + margin" and the configuration keys `manual_margin` and `manual_duration_hours` of the first design are no longer used.
- **FR-MAN-3** The expiry is decided by the boiler Pi: it adds 3 hours (On) or 1 hour (Off) to its clock and rounds to a full hour (one more hour after minute 29), so On lasts about 2.5 to 3.5 hours and Off about 30 to 90 minutes. The boiler service deletes the file at that time and the schedule applies again. The Orchestrator does nothing at expiry.
- **FR-MAN-4** While an override is active it takes precedence over `Cal.json`. A new manual action replaces the previous one.
- **FR-MAN-5** "Manual active" is derived only from the status endpoint: `Status == "Manual"` means a manual override is in use, `Auto` means the schedule, `Off` means off. The UI and MQTT show this value; no local override state is stored. The expiry time is not exposed by any endpoint, so it is shown as "reverts to Auto by itself when the manual time ends".
- **FR-MAN-6** The same function is available through the UI, MQTT and the e-mail command. E-mail commands keep the sender validation and the two-factor confirmation of FR-LEG-3 and FR-LEG-4 (nothing changes until the token is returned). Confirmation of the action is done by re-reading the status after the POST and showing the result.
- **FR-MAN-7** Cancelling an override before expiry (Auto) is `POST auto/` (FR-MAN-1). It is available in the UI, MQTT and e-mail (`auto` command).

### 4.4 MQTT / Home Assistant (FR-MQTT)

- **FR-MQTT-1** The system connects to a configurable MQTT broker (host, port, user, password, TLS option, base topic) with automatic reconnect and a last-will "offline" message.
- **FR-MQTT-2** Home Assistant MQTT Discovery messages are published so the entities appear without manual YAML:
  - sensors: three temperatures, both capacities, target, min, minutes-to-start;
  - binary sensors: heater on, active;
  - switch or buttons: manual boiler ON / OFF buttons (and cancel, if available);
  - switches: one per relay in `TimeCal.json`.
- **FR-MQTT-3** State is published (retained) on each change and at least once per minute.
- **FR-MQTT-4** Commands are accepted on command topics, validated, and handled exactly like UI actions (FR-MAN, section 4.1).
- **FR-MQTT-5** Manual commands received through MQTT carry an optional duration (default 3 h). Decision: the duration is `hours` in the JSON payload (`{"action": "on", "hours": 2}`), from 15 minutes to 12 hours (the manual file holds only a weekday and a clock time); anything else is refused. Relay switches in Home Assistant run `[mqtt] relay_on_seconds` (default 600 s) or the `seconds` of a JSON payload. Retained command messages are ignored. When the reading is missing, old or the boiler Pi is down, the state carries no values (entities become unknown) instead of old ones.
- **FR-MQTT-6** MQTT can be disabled by configuration without affecting the other features.

### 4.5 Google access (FR-GOOG)

- **FR-GOOG-1** Access to Google Calendar and Gmail uses OAuth 2.0 with a pre-provisioned client credential and token. The application name (now hard-coded as "Google Calendar API .NET" / "Google Gmail API .NET"), client secret file (`CLIENT_SECRET_FILE`), token file locations and calendar id are configurable. Scopes: calendar read-write (the existing code requests read-only), and full Gmail access `https://mail.google.com/` (needed to read and delete command mails).
- **FR-GOOG-1a** The sender address used when sending mail is the authorized account, not the placeholder address hard-coded in `GmailMessages.py`.
- **FR-GOOG-1b** The `oauth2client` library is replaced by `google-auth`/`google-auth-oauthlib`; a token file from the old flow may need one re-authorization.
- **FR-GOOG-2** The token is refreshed automatically. Secrets are stored outside the schedule folder with restricted file permissions and are never logged or shown in the UI.
- **FR-GOOG-3** Authorization (consent in a browser) is done once, and again only if the token is revoked, using a small command-line tool (`python -m orchestrator.auth`) that runs Google's "installed application" flow: it starts a temporary local web server on a configurable port, shows the Google consent page, and stores the token file (mode 600, outside the project folder). Three ways to use it, all documented: (a) **on the Pi itself with a desktop and browser installed** (the chosen setup; see FR-GOOG-6); (b) on another PC, then copy the token file to the Pi; (c) from a PC over SSH with a port forward (`ssh -L 8080:localhost:8080 pi@host`) while the tool runs on the Pi with `--no-browser`, which prints the URL to open. Google's device-code flow is not an option because it does not allow the Gmail and Calendar scopes.
- **FR-GOOG-4a** Migration of the existing tokens: the old scripts store `oauth2client` token files in a `.credentials` folder (in the working directory the old script ran from): `Gmail-python-quickstart.json` (scope `https://mail.google.com/`) and `Calendar-python-quickstart.json` (scope calendar read-only), created with the client file `client_secret.json`. The auth tool has an import option (`python -m orchestrator.auth --import-oauth2client <folder>`) that converts them to the new format (it needs only `refresh_token`, `client_id` and `client_secret` from them) and checks with Google that the refresh token still works. The Gmail token can be reused as is. The Calendar token is read-only, so it can be reused for reading, but writing UI changes back to the calendar (FR-CFG-4) needs a new consent with the read-write calendar scope. Reuse works only if the same `client_secret.json` (the same Google Cloud client) is used, the token was not revoked, and it has not expired (see FR-GOOG-5). The copied files are secrets: mode 600, never in the project repository (listed in `.gitignore`).
- **FR-GOOG-5** Token lifetime: the consent screen of the Google Cloud project must be set to **"In production"** (a personal-use app can stay unverified, which only shows a warning at consent time). In "Testing" mode Google expires the refresh token after 7 days and the service would lose Calendar and Gmail access every week. A token unused for 6 months also expires. The tool checks and reports the token expiry state.
- **FR-GOOG-6** If the Pi has a desktop environment for this authorization, the Pi still boots to the command line by default (`raspi-config` → Boot Options → Console), so the desktop does not use the Pi 3's 1 GB RAM while the service runs; the desktop is started only when authorization is needed (`startx` or a temporary change of the boot target). A desktop adds about 2-3 GB, so use a 32 GB card. Image: **Raspberry Pi OS (32-bit) with desktop** (the Pi 3 has 1 GB RAM, and 64-bit programs use noticeably more memory for no benefit at this size); fall back to the 64-bit image only if the install check (CS-1a) shows that a needed library has no 32-bit build. Switch to the console boot with `sudo raspi-config` → System Options → Boot / Auto Login → Console, and start the desktop when needed with `sudo systemctl start lightdm` (stop it again with `sudo systemctl stop lightdm`).
- **FR-GOOG-7** When authorization is lost (revoked, expired, invalid), the service shows "Google authorization needed" on the UI (header chip and System tab), publishes it to Home Assistant, and sends the admin an e-mail only if mail still works (otherwise the other two channels are the alert). It keeps running on the last valid files.
- **FR-GOOG-4** If Google is unreachable, the system keeps running on the last valid local files, retries with backoff, and shows "calendar offline" in the UI.

### 4.6 Config distribution (FR-PUSH)

- **FR-PUSH-1** After each accepted change the Orchestrator saves the schedule locally (`Cal.json` / `TimeCal.json`) and POSTs the file as multipart form field `file` to `PostUpdateCalURL` (boiler) or `PostUpdateRelayURL` (timer). Only the schedule that changed is sent.
- **FR-PUSH-7** File format compatibility. The timer service (and boiler service) read the schedule files with the string-splitting parser in `TimerCalander.py` / `BoilerCalander.py`, not a JSON parser, so the Orchestrator must write exactly what the existing `tojson()` writes:
  - compact text with no spaces or newlines, objects separated by `},{`, no trailing newline and no byte-order mark, UTF-8;
  - key order `DayOfWeek, Hour, Target, Min` (boiler) and `DayOfWeek, Hour, State, RelayNum` (timer); `Hour` always `HH:MM:SS`; numbers unquoted;
  - entries sorted by day then time, exact duplicates removed;
  - an empty **schedule** (`Cal.json`, `TimeCal.json`) is never pushed (the existing writer would produce an invalid `]`). The only exception is an empty manual file, written as `[]` (FR-MAN-1).
  A test compares the Orchestrator output byte-for-byte with the output of the existing classes for the current `Cal.json` and `TimeCal.json`.
- **FR-PUSH-8** The same file POST is used for `manual.json` and `<n>Timermanual.json` (section 3.6). The upload sends only the file: the existing `Post()` also sends a second, JSON request after a file upload and reports failure; the Orchestrator must not.
- **FR-PUSH-2** Endpoint URLs and the request timeout are configurable. No FTP/SFTP is used.
- **FR-PUSH-3** A push is successful only if the HTTP status is 2xx. The response text is logged. The local copy is the "last pushed" reference used to detect changes.
- **FR-PUSH-4** A failed push is retried with backoff and stays pending (shown in the UI) until it succeeds. Pushing is idempotent, and the local file is not marked as pushed before success.
- **FR-PUSH-5** A "push now" action in the UI re-sends both files. The boiler Pi is not polled while it reports the connection-failure placeholder (as in the existing script); the push resumes once it responds.
- **FR-PUSH-6** The Orchestrator runs on a machine other than the boiler Pi (Pi 3 or any LAN host) and needs only HTTP access to the boiler Pi.

### 4.7 Status acquisition (FR-STA)

- **FR-STA-1** The Orchestrator obtains boiler state by polling `GET /status` on the boiler Pi (URL configurable, request timeout 5 s). If it is unreachable the UI shows "boiler not responding" with the time of the last good reading; values are never invented.
- **FR-STA-2** The reader polls at a configurable interval (default 10 s).
- **FR-STA-3** Staleness is detected from the `Date` field.
- **FR-STA-4** Missing or unreadable data produces "unknown" values, not zeros.
- **FR-STA-5** A malformed or incomplete `/status` response is treated as unreadable (FR-STA-4).

### 4.8 Features carried over from `BoilerControler.py` (FR-LEG)

Kept unless you say otherwise (OQ-11):
- **FR-LEG-1** Main loop every `RefreshTime` seconds: read status, process incoming mail commands, process calendars.
- **FR-LEG-2** Admin e-mail when the boiler Pi stops responding and when it recovers (sent once per transition), and when a calendar is created, modified (with a readable diff of added/removed slots) or cannot be read.
- **FR-LEG-3** E-mail commands accepted only from the authorized address list (`UserEmailList`, see FR-LEG-3b) and confirmed by two-factor (FR-LEG-4): `status`, `log` (last 150 lines), `on`, `off`, `auto`, `switch <relay 2-7> <seconds >10>` and `reset` (reboot of the boiler Pi over SSH, kept). `auto` is new and also needs the two-factor confirmation.
- **FR-LEG-3a** The reboot runs `sudo reboot` on the boiler Pi over SSH with paramiko: key-based login preferred (password only from the secrets file), host key checked against a stored fingerprint, connect and command timeouts, no busy-wait. A dropped connection after sending the command counts as success. The result ("reboot requested") is e-mailed, and the status endpoint is watched until the Pi answers again (the down/up alerts of FR-LEG-2 are suppressed for a configurable grace period, default 5 min, after a requested reboot).
- **FR-LEG-3b** Sender validation (kept): the address in the `From` header (the part inside `<...>` if present) is compared, case-insensitively and trimmed, with the `UserEmailList` (`;`-separated, configuration). Mail from any other sender is ignored (no reply to the sender, so the address is not confirmed to strangers), logged, and still deleted from the inbox, **and a security alert is e-mailed to the alert address** (`SecurityAlertEmail`, configuration, set to `emarelly@gmail.com`). The alert contains: time received, sender address and display name, recipient address, subject, the first 500 characters of the body (plain text, links not followed), the authentication result (SPF/DKIM) when available, and whether the subject looks like a command. Alerts are rate-limited to protect the inbox and avoid loops: one alert per sender per hour with a count of the mails suppressed, a daily maximum (default 20), and no alert for mail from the system's own address or for automatic mail (bounces, `Auto-Submitted` header). A rejected confirmation token from an authorized sender (FR-LEG-4) triggers the same kind of alert. Commands are recognised by the first word of the subject (`status`, `log`, `on`, `off`, `auto`, `switch`, `reset`), not by a substring match. Because a `From` header can be forged, mail is additionally accepted only if Gmail's authentication result for it is a pass (SPF or DKIM) when that header is present.
- **FR-LEG-4** Two-factor confirmation (kept) for every command that changes something (`on`, `off`, `auto`, `switch`, `reset`); `status` and `log` need none:
  1. The command mail gets a reply whose subject is a random 10-letter token (from a cryptographic random source); the reply body shows the pending command and the current status.
  2. The command is stored with the token, the sender and the time. Only the latest pending command exists; a new command replaces it.
  3. The command runs only when a mail **from the same sender** returns the token in its subject within 120 s (configurable). A token works once.
  4. An expired or wrong token counts as a failure and the sender is told. After `MaxFailures` (default 5) failures, e-mail commands are blocked for a lockout period (default 15 min) and the admin is notified; a correct confirmation resets the count.
  5. The "request done" mail reports the real outcome (success or the error), not just "done".
- **FR-LEG-5** Calendar changes are detected by comparing with the last saved copy and are pushed only when different (FR-PUSH-1).
- **FR-LEG-6** The relay switch command (relay 2-7, duration in seconds) is exposed in the UI, MQTT and e-mail. It is `POST relayon/` (on) or `POST relayoff/` (off) with the one-line JSON body `{"swith": <relay>, "duration": <seconds>}` (the key is spelt `swith` by the boiler service); the boiler Pi builds the relay's manual file and acts about 90 seconds later. **A duration of 0 or less means on / off without a time limit** (a single entry, the relay stays in that state until the next command); a duration of more than 10 s and at most 24 h switches the relay on (off) and back off (on) after that time. The Orchestrator sends 0 for any value of 0 or less. The UI and MQTT tell the user what 0 means; the e-mail `switch` command keeps its timed form (more than 10 s).

## 5. Non-functional requirements

- **NFR-1 Platform**: Raspberry Pi 3 (1 GB RAM, ARMv8 CPU running a 32-bit OS). Python 3.13.5 (as installed, see CS-1). Typical RAM use below 150 MB and idle CPU below 10%.
- **NFR-1a Pi 3 performance budget** (measured on a real Pi 3 before release, with the UI open on two clients):
  - **Rendering happens in the browser.** The Pi serves one static HTML page (target ≤ 60 KB, ≤ 20 KB gzipped, no frameworks, no external libraries or fonts, charts and gauges as inline SVG/CSS) and small JSON responses. The page is served gzip-compressed with cache headers. The Pi never renders pages, images or charts itself, and Chromium is not run on the Pi.
  - **One upstream poll, many clients.** The service polls the boiler Pi `/status` once every 10 s and caches the result; browser requests are answered from the cache (≤ 5 ms), so the load does not grow with the number of open pages. `/history` is fetched at most once a minute (the boiler Pi adds a sample about every 10 min) and cached; the page asks for it every minute while visible and at once when the tab becomes visible again. Browser pages poll only while visible, and redraw only when data changed.
  - **Budgets:** resident memory ≤ 120 MB in steady state (≤ 150 MB peak during a calendar read); average CPU ≤ 5% of one core, peaks ≤ 50% for under 5 s; UI API response time ≤ 100 ms at the 95th percentile; first page load ≤ 2 s on the LAN; start-up to ready ≤ 30 s.
  - **Heavy parts are loaded on demand.** The Google API client, `astral` and `paramiko` are imported only when first needed (calendar read, astro time, reboot) so they do not stay in memory otherwise; the location is cached (FR-CFG-6a) so no network geocoding happens per read. Calendar reads and Gmail checks run at their own intervals (5 min and 30 s by default), never in the request path of the UI.
  - **Server:** **Flask served by `waitress`** (pure-Python production WSGI server, threaded, no compilation on the Pi; the Flask development server is not used), in a single process. Background work (status poll, calendar sync, Gmail check, MQTT client) runs in a few worker threads that write to a shared, lock-protected state cache; HTTP handlers only read that cache. Static files are served pre-compressed (gzip). No database server, no message broker beyond the MQTT client, no Node.js, no reverse proxy (LAN only).
  - **SD card:** log files rotate at a fixed size (default 2 MB × 3); the service writes files only when content changes (FR-CFG-10).
  - **Check:** a script reports memory (RSS), CPU and response times during a 1-hour run, and the budgets above are acceptance criteria.
- **NFR-2 Autonomy**: runs as a systemd service, starts at boot, restarts on failure, needs no internet for core operation.
- **NFR-3 Safety**: no failure of Google, MQTT, the REST push or the UI may switch the heater or relays into an unintended state. On loss of the schedule the last valid files continue to apply.
- **NFR-4 Time**: a single timezone (configurable); daylight saving changes handled; NTP assumed. The Pi has no battery clock, so before the clock is synchronised no schedule writes or overrides are created.
- **NFR-5 Storage**: on an SD card, so logs are rotated (size-limited) and writes are kept to a minimum. The installed 16 GB card (15 GB file system, 8.5 GB free with the desktop image) is sufficient: the virtual environment needs about 0.3 GB, logs at most 20 MB, data a few MB. Use an endurance-rated or A1/A2 card from a known brand.
- **NFR-6 Configuration**: all settings are in one config file (INI or JSON), no hard-coded paths or credentials. Changes are applied on restart.
- **NFR-7 Logging**: see section 5b.
- **NFR-8 Security**: LAN only, no inbound internet exposure, no credentials shown in the UI or written to logs.
- **Secrets from environment variables.** Passwords are not stored in `Config.py` or any file in the project. They are read from environment variables (proposed names: `BOILER_SSH_USER`, `BOILER_SSH_PASSWORD`, `MQTT_PASSWORD`, `UI_PASSWORD`; the Google client-secret and token files are referenced by path settings, `GOOGLE_CLIENT_SECRET_FILE`, `GOOGLE_TOKEN_FILE`). On the Pi they are supplied to the service through a systemd `EnvironmentFile=` that is owned by root with mode 600 and kept outside the project folder; on Windows during development they are normal user environment variables. Start-up fails with a clear message (naming the variable, never its value) if a required one is missing.
- **Better option for the SSH reboot:** use an SSH key (private key file path in `BOILER_SSH_KEY_FILE`, mode 600) instead of a password, so no password exists at all. The password variable remains as a fallback.
- **NFR-9 Maintainability**: see section 5a.

## 5a. Coding standards (CS)

**Language and tooling**
- **CS-1** The Pi runs **Python 3.13.5** (Raspberry Pi OS "Trixie", 32-bit). The code targets **Python 3.11 or newer** (the oldest version on supported Raspberry Pi OS releases) and is tested on 3.13, so current language features are used: built-in generics (`list[str]`, `dict[str, int]`), `X | None` unions, `match`, `tomllib` (TOML configuration), `StrEnum`, `dataclass(slots=True)`, `zoneinfo` with the `tzdata` package, `ExceptionGroup`, `Self`. Not used: the 3.12-only `type` statement and PEP 695 generic syntax (the minimum is 3.11), anything newer than 3.13, and the modules removed in Python 3.13 (`cgi`, `imghdr`, `telnetlib`, `pipes`, `distutils` and the other "dead batteries"), nor libraries that need them. The development machine must run Python 3.11 or newer so that the check command (CS-4) gives the same result there. The old Python 3.7.3 / Buster image is gone; the 3.7 and 3.9 restrictions no longer apply.
- **CS-1b** Target platform, confirmed on the Pi: Raspberry Pi OS (Debian "Trixie"), Python 3.13.5, **32-bit** (`getconf LONG_BIT` = 32, `armv7l`), 15 GB root file system with 8.5 GB free after installing the desktop image, time zone `Asia/Jerusalem`, NTP active and the clock synchronized. Consequences: binary packages come from piwheels (the default pip index on Raspberry Pi OS) for Python 3.13 / armv7l; the virtual environment needs `sudo apt install python3-venv python3-dev libffi-dev libssl-dev`; a system-wide `pip install` is blocked by the OS (PEP 668), so all installs go into the virtual environment; systemd is new enough for cgroup v2 (`MemoryMax`) and the watchdog; the default time zone setting of the service is read from the OS (`Asia/Jerusalem`) and can be overridden in the configuration.
- **CS-1a** Library versions: `requirements.txt` lists the libraries unpinned and `bash tools/check_pi_install.sh` on the Pi installs them in a throw-away virtual environment, tests the imports and an astral/time-zone calculation, reports memory use and writes `requirements.lock` with the exact working versions, which is what is deployed (CS-17). Development tools are in `requirements-dev.txt` (not installed on the Pi). Pre-check on 2026-10-24 (PyPI and piwheels file lists, not an install): every library with compiled code (`cryptography`, `bcrypt`, `pynacl`, `cffi`, `markupsafe`) has ready-made wheels for 64-bit ARM (PyPI) and for 32-bit ARM (piwheels) for Python 3.11 and 3.13; all other dependencies are pure Python. Neither the 32-bit nor the 64-bit image is blocked by a library; the 32-bit image was chosen for memory (FR-GOOG-6).
- **CS-2** Style is PEP 8, enforced automatically: `black` (line length 100) for formatting and `ruff` for linting and import sorting. Names are `snake_case` for functions and variables, `PascalCase` for classes, `UPPER_CASE` for constants. The misspellings of the legacy code (`Calander`, `Controler`, `swith`, `streat`) are not carried over, except where an external interface requires them (the `swith` JSON key, the endpoint paths, the config key names in section 3.6).
- **CS-3** Type hints on all function signatures; `mypy` runs clean on the whole package. Data structures (slot, timer entry, status, config) are `dataclass`es (frozen where possible), not loose dicts or strings parsed by splitting.
- **CS-4** One command (`python -m tools.check`) runs formatting check, lint, type check and tests; the same command is used before every commit (pre-commit hook) and is the definition of "green".

**Structure**
- **CS-5** A package `orchestrator/` with small single-purpose modules: `config`, `models`, `schedule_files` (serializer and parser, FR-PUSH-7), `validation`, `calendar_source` (Google read/write and event title grammar), `astro`, `boiler_client` (REST), `status_cache`, `manual` (manual file builder), `mail_commands` (sender check, 2FA state machine, alerts), `mqtt_bridge`, `ssh_reboot`, `web` (Flask app, API, static files), `app` (wiring and thread start), `__main__`.
- **CS-6** Pure logic (parsing, validation, value computation, state machines, time arithmetic) is separate from I/O (HTTP, Google, MQTT, files, SSH, clock). I/O sits behind small interfaces so tests can replace it with fakes. The current time comes from an injectable clock, never from scattered `datetime.now()` calls.
- **CS-7** No global mutable state and no work at import time (the legacy modules parse command-line arguments and open network connections on import). Dependencies are passed in explicitly. Nothing imports from `ref files`; legacy behaviour is ported with tests and the legacy files are only read for reference.
- **CS-8** Configuration is one file (TOML via `tomllib`, preferred, or JSON) plus environment variables for secrets (section 5, NFR-8), loaded once into a validated, immutable config object. Unknown or invalid keys stop start-up with a clear message that names the key.

**Error handling and robustness**
- **CS-9** No bare `except:` and no silent `pass`. Catch specific exceptions, with a small project exception hierarchy (`ConfigError`, `BoilerUnreachable`, `ValidationError`, `CalendarError`, `AuthError`). Every network call (HTTP, Google, MQTT, SSH) has an explicit timeout.
- **CS-10** Retries use exponential backoff with jitter and a maximum; they are used only for idempotent operations (reads, schedule uploads). Manual commands are not retried automatically.
- **CS-11** Every background loop catches errors per iteration, logs them with the traceback, and continues, so one failure never stops the service (NFR-3). Failures that change the safe state (cannot read the status, cannot reach the boiler) are reported as "unknown" or "error", never as a made-up default value.
- **CS-12** Shared state is held in one place behind a lock and handed out as immutable snapshots. Threads are daemon threads with a stop event; `SIGTERM` (systemd stop) shuts everything down cleanly within 5 s.
- **CS-13** Time handling uses timezone-aware datetimes everywhere; day-of-week conversion (1 = Sunday) lives in one function with tests for week and daylight-saving boundaries.
- **CS-14** Files are written atomically (write to a temporary file in the same directory, flush, `os.replace`), UTF-8 without BOM, in the exact format of FR-PUSH-7.

**Security**
- **CS-15** All input from the UI API, MQTT, e-mail and the calendar is validated (types, ranges, lengths, the ≤ 5 limit) before use. The web API accepts JSON only, checks the `Origin`/`Host` header on state-changing requests (CSRF), limits request size, and rate-limits failed logins. No shell is invoked with user-supplied text; the only remote command is the fixed `sudo reboot`.
- **CS-16** The service runs as an unprivileged user (not root) with systemd hardening (`NoNewPrivileges=yes`, `ProtectSystem=strict`, `ProtectHome=read-only`, `PrivateTmp=yes`, `ReadWritePaths=` limited to the data and log folders).
- **CS-17** Dependencies are few and pinned to exact versions in `requirements.txt` (flask, waitress, requests, paho-mqtt, google-auth, google-auth-oauthlib, google-api-python-client, astral, paramiko, tzdata, sdnotify; the exact working versions come from `requirements.lock`, CS-1a; `geopy` only in the one-time location setup tool). `pip-audit` is run before each release.

**Testing and documentation**
- **CS-18** Tests use `pytest`. Required unit tests: the file serializer byte-for-byte against the current `Cal.json` and `TimeCal.json` and parsing of every file in `ref files`; validation rules; the calendar event-title grammar (every example, plus the cases the legacy code crashes on); astro resolution across a daylight-saving change; manual ON/OFF value calculation (cap 5, margin, week rollover); the two-factor state machine (expiry, one-time use, lockout, wrong sender); the unauthorized-sender alert and its rate limits; status mapping (highest = Upper).
- **CS-19** Integration tests run the service against a fake boiler Pi (a small Flask app that mimics `/status`, `/history` and the upload endpoints) and a fake MQTT broker, covering: push on change, retry after failure, boiler offline and recovery, manual On/Off/Auto.
- **CS-20** Target coverage is 85% of the core logic modules (CS-6 "pure logic"); I/O adapters are covered by the integration tests. A defect found in production gets a regression test first.
- **CS-21** Public functions have short docstrings (what, arguments, errors raised); non-obvious decisions are explained in comments (why, not what). A `README.md` covers install on a Pi, environment variables, running as a service, and troubleshooting; a `CHANGELOG.md` lists changes per version; the version is a single constant.
- **CS-22** Git: small commits with imperative messages (`Add manual file builder`), one topic per commit; the `main` branch always passes `python -m tools.check`.

## 5b. Logging (LOG)

- **LOG-1** Only the standard `logging` module is used; there is no `print`. Each module gets `logger = logging.getLogger(__name__)`. Logging is configured in one place (`dictConfig` at start-up) and nowhere else.
- **LOG-2** Handlers: a rotating file (default 2 MB × 3, from NFR-1a) for the main log, the console for systemd/journald (journald kept in volatile storage on the Pi to spare the SD card), and an in-memory ring buffer (last 200 events) that feeds the System tab of the UI. The log level and the file location are configuration.
- **LOG-3** Format: one line per event, ISO 8601 timestamp with milliseconds and UTC offset, level, logger, thread, message: `2026-10-24T16:40:19.707+03:00 INFO  orchestrator.manual [web-3] event=manual_on source=ui target=4.4 min=4.4 expires=7/19:40:00 result=ok`. Messages carry `key=value` context (event name, source of the request: `ui`/`mqtt`/`email`/`calendar`, result, duration in ms, relay number). A JSON-lines format can be switched on by configuration.
- **LOG-4** Level policy:
  - `DEBUG`: request and response payloads (secrets masked), parsed calendar events, timings. Off by default.
  - `INFO`: state changes and actions: mode change, schedule changed in calendar or UI, file pushed, manual command accepted and done, boiler Pi down or up, MQTT connected or disconnected, service start and stop.
  - `WARNING`: recoverable problems: a failed attempt that will be retried, boiler not responding, stale status, input rejected by validation, a calendar event that cannot be parsed, an unauthorized e-mail.
  - `ERROR`: an operation failed after retries or an unexpected exception (with traceback).
  - `CRITICAL`: the service cannot continue (bad configuration, cannot bind the port); it exits and systemd restarts it.
- **LOG-5** No noise: a poll that changes nothing is not logged; "boiler down" is logged once when it starts and once when it ends (with the duration), not every 10 s; repeated identical warnings are collapsed (`... repeated 37 times in 10 min`). Third-party libraries (`urllib3`, `googleapiclient`, `paramiko`, `waitress`, `werkzeug`) are set to `WARNING`.
- **LOG-6** Exceptions are logged once, at the place where they are handled, with `exc_info` (traceback); code does not both log and re-raise the same error.
- **LOG-7** Never logged: passwords, OAuth tokens and client secrets, the two-factor token (only a short id such as the first two letters), `Authorization` headers, full e-mail bodies. A logging filter masks any value whose key looks like a secret. E-mails are logged as sender, truncated subject and decision only.
- **LOG-8** A separate **audit log** (own file, 1 MB × 5, same format) records every state-changing action and security event: who (UI user, MQTT client, e-mail address), through which channel, what (manual On/Off/Auto, relay switch, reboot, schedule edit with old → new values), and the result; plus rejected commands, unauthorized senders, failed logins and two-factor lockouts. It is never cleared by the service.
- **LOG-9** Each command gets a short correlation id that appears in every line it produces (UI request → manual file → upload → status check → confirmation mail), so one action can be followed from start to end.
- **LOG-10** The level can be changed at run time without a restart (System tab, or `SIGUSR1` toggles `DEBUG` for 15 minutes and then returns to the configured level). The System tab shows the ring buffer and offers a download of the current log file, with secrets masked.
- **LOG-11** At start-up one block logs the version, Python version, host, configuration summary (secrets shown as `***`), the clock-sync state and the result of the self-checks; an hourly `INFO` heartbeat logs uptime, memory (RSS), queue sizes, and last-success times of the status poll, calendar read and mail check, and also supplies the data for the Pi 3 performance check (NFR-1a).
- **LOG-12** Total log storage is capped (main + audit ≤ 20 MB). Tests verify that key events are logged (`caplog`) and that no secret value appears in any log output.

## 5c. Service start-up and monitoring (OPS)

**Start**
- **OPS-1** The Orchestrator is a **systemd service** (`orchestrator.service`), enabled at boot, running as an unprivileged user from a Python virtual environment: `ExecStart=/opt/orchestrator/venv/bin/python -m orchestrator`. It starts after `network-online.target` and `time-sync.target` (the Pi 3 has no battery clock, NFR-4), has `Restart=on-failure`, `RestartSec=10`, a start-rate limit (5 starts per 10 min, then it stays failed and an alert is raised), `TimeoutStopSec=15`, a memory cap (`MemoryMax=300M`; the OS now uses systemd with cgroup v2, where `MemoryMax=` works; on an old Buster image with systemd 241 `MemoryLimit=` would be needed), so a leak restarts the service instead of freezing the Pi), and reads its secrets from `EnvironmentFile=/etc/orchestrator/orchestrator.env` (root-owned, mode 600, NFR-8). Logs go to the journal (`journalctl -u orchestrator`) and the log files of section 5b.
- **OPS-2** Start-up sequence: (1) load and validate the configuration, stopping with a clear message on error; (2) wait up to 2 minutes for clock synchronization (continue with a warning, and make no schedule writes or manual files until it is synchronized); (3) load the last good schedule files from disk; (4) start the worker threads (status poll, calendar sync, mail check, MQTT, file push queue); (5) start the web server; (6) tell systemd the service is `READY` (`Type=notify`) once the web server is listening. The service does **not** wait for the boiler Pi, Google or MQTT: if one is down it starts in a degraded state and reports it (so a power cut that brings the Pi up before the router does not leave the service dead).
- **OPS-3** Start-up self-check, logged and shown on the System tab: configuration, secrets present (names only), clock sync, free disk space, boiler Pi reachable, Google token valid, MQTT connected. The admin gets one e-mail after each start ("Orchestrator started", version, reason of the previous stop if known) once the mail client is available.
- **OPS-4** Install and update by a script (`install.sh`): create the user and virtual environment, install the pinned requirements, install the unit and the environment-file template, enable the service. An update is: stop, replace the code, `pip install -r requirements.txt`, start. The previous version stays in place for rollback. Operations are documented in the README (`systemctl start|stop|restart|status orchestrator`).
- **OPS-5** Safe on restart or power loss: all schedule files and the last push state are on disk, and the manual override lives on the boiler Pi, so the boiler and timer services keep working with their last files whether the Orchestrator is running or not (NFR-3). After a restart the Orchestrator compares its files with the last pushed ones and pushes again only if they differ.

**Monitoring (four layers)**
- **OPS-6 Process level (systemd).** A crash restarts the service. A hang is caught by the systemd watchdog (`WatchdogSec=60`): the service must send a watchdog ping at least every 30 s, and it sends it **only while the internal health check passes** (OPS-7). Optionally the Pi's hardware watchdog (`RuntimeWatchdogSec=15`) reboots the Pi if the operating system itself hangs.
- **OPS-7 Inside the service.** A supervisor thread tracks a heartbeat from each worker (status poll, calendar sync, mail check, MQTT, push queue). A worker thread that died is restarted. A worker that has not completed a cycle within 5× its interval is marked **failed**; critical failures (status poller, web server, supervisor) stop the watchdog ping so systemd restarts the service. Expected external failures (boiler offline, Google unreachable) mark the component **degraded**, not failed, and never trigger a restart.
- **OPS-8 Health endpoint.** `GET /healthz` (no login, minimal data, LAN only) returns HTTP 200 when everything is `ok` or `degraded` and 503 when a component is `failed`. The JSON lists each component with state, last success time, last error text (no secrets), plus version, uptime, memory (RSS), CPU temperature, free disk space and clock-sync state. The header chips and the System tab of the UI use the same data. It is cheap (answered from the cache) so any external checker can poll it every minute.
- **OPS-9 Home Assistant (MQTT).** The service publishes an availability topic with a last-will message, so Home Assistant shows the Orchestrator as **offline** within the keep-alive time (default 60 s) if it dies, hangs, or loses the network. It also publishes diagnostic entities: version, uptime, memory, CPU temperature, last calendar sync, pending file pushes, number of failed components. This is the only monitoring that still works when the Orchestrator itself is dead, so Home Assistant should notify on "offline" (documented in the README).
- **OPS-10 E-mail alerts to the admin.** Sent once per problem and once when it is resolved, rate-limited like the other alerts (FR-LEG-3b): boiler Pi down or restored (kept from the old script), calendar read failing 3 times in a row, a file push pending for more than 15 minutes, Google token expired or revoked (needs re-authorization), free disk space below 10%, memory above 150 MB for 10 minutes, CPU temperature above 80 °C, clock not synchronized after 10 minutes, service restarted by the watchdog, start-limit reached.
- **OPS-11** Every monitoring event is logged (section 5b) and the hourly heartbeat line carries the key figures, so a problem seen in Home Assistant or by e-mail can be traced in the journal. The Pi 3 performance check (NFR-1a) uses the same figures.

## 6. Data validation rules

- `DayOfWeek` 1–7; `Hour` is `HH:MM:SS`; slots unique per day and time and sorted.
- `0 <= Target <= 5` and `0 <= Min <= 5` (the heater limit, configurable but 5 by default). `Min > Target` is accepted with a warning, not rejected: the real `Cal.json` uses it (for example Sunday 13:00 with Target 3.0 and Min 3.5, meaning keep at least 3.5). This applies to calendar events, UI edits and manual overrides alike; a calendar event or UI value above the limit is rejected and reported, never clamped silently.
- Timer: `State` 0/1, `RelayNum` within the configured relay list. A relay's ON/OFF entries should alternate; report a warning otherwise.

## 7. Acceptance criteria (summary)

1. Editing a slot in the UI updates Google Calendar and both JSON files within 1 minute, and the boiler Pi receives the file by POST.
2. Editing the calendar changes the UI and files within one polling interval.
3. Manual ON from the UI and from Home Assistant makes `/status` report `Manual`; after the expiry time (3 h) it reports `Auto` again with no action from the Orchestrator.
4. Home Assistant discovers all entities and shows live values.
5. With the internet cable unplugged for 24 h, heating and relays follow the last schedule, and the system recovers on reconnect without manual steps.
6. A corrupted or invalid input never replaces a valid schedule file.
