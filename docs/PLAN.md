# PLAN.md - Definition of Done and work plan

Used by `/loop`: each iteration takes the **first unchecked item whose dependencies are checked**, finishes it completely, ticks it, and stops when nothing automatable is left. `Requirements.md` defines *what*; this file defines *when it is done*. Rules for how to work are in `CLAUDE.md` (safety rules, per-change definition of done).

## 1. Project Definition of Done

The project is done when **all** of these are true:

1. Every milestone M0-M7 below is fully checked (built and tested without the real Pi, Google or Home Assistant).
2. `python -m tools.check` (black, ruff, mypy, pytest) passes with no new warnings on Python 3.11 and on 3.13, coverage of the core-logic modules is at least 85%.
3. Every requirement ID in `Requirements.md` (FR-*, NFR-*, CS-*, LOG-*, OPS-*) appears in `docs/traceability.md` with either a test name or "manual check on the Pi" (M8). No ID is unmapped.
4. The serializer reproduces the current `Cal.json` and `TimeCal.json` byte-for-byte.
5. No secret value appears in the repository, in any log output (tested) or in any test fixture; no test contacts a real host.
6. `README.md` explains install on the Pi, environment variables, running as a service, Google authorization, and troubleshooting; `CHANGELOG.md` exists.
7. Milestone M8 (acceptance on the real Pi) is signed off **by the user**. The loop never ticks M8 itself.

## 4. Loop rules

- **Validation step (after every item), capped at 5 failures.** The loop keeps going item by item until the project DoD (section 1) is met. After finishing an item it must pass this validation before the item is ticked:
  1. `python -m tools.check` is green (black, ruff, mypy, pytest) with no new warnings, no skipped or weakened tests, no `# noqa` / `# type: ignore`.
  2. The item's own acceptance is demonstrated by a test (for example the golden-file byte comparison for the serializer) and the requirement IDs it covers are listed in `docs/traceability.md`.
  3. Every line of the review checklist in `CLAUDE.md` that applies to the item is checked against the diff (parser compatibility, day-of-week conversion in one place, 5-shower cap on all channels, manual expiry semantics, DST astro times, relays 2-7 only, locked cache, e-mail checks, no legacy defects, no real hosts or golden-file changes).
  4. The DoD items that can be checked now (section 1, items 2-6) are still true: nothing previously ticked is broken.
  If validation fails, the loop fixes the cause and validates again. Each failed validation adds 1 to `Failed validations in a row` in section 6; a pass resets it to 0 and ticks the item. **When the counter reaches 5, the loop stops** (end it with `ScheduleWakeup` `stop: true`), leaves the item unticked, writes under "Blocked / decisions needed" what failed in each attempt and what it thinks is wrong, and reports. The user resets the counter to 0 to continue.
- One item per iteration, or several small related items of the same milestone, each validated separately. Never leave a half-finished item when stopping: finish it, or revert it and say so under "Blocked / decisions needed". Read `CLAUDE.md` and this file first; pick the first unchecked item with its dependencies done; write tests first or together with the code; run `python -m tools.check`; tick the box; update `docs/traceability.md` for the IDs covered.
- **Stop and ask** (write the question under "Blocked" below and end the loop) when an item needs an open question (OQ-4, OQ-10, OQ-14, OQ-16, OQ-17), a real host, a real credential, a new dependency, or a change to a golden file. Use config keys and `DRY_RUN` for undecided values; do not invent.
- Stop the loop when every M0-M7 box is checked or only blocked items remain, and report what is left.
- Never tick an item whose test is skipped, weakened or missing, and never tick M8.
